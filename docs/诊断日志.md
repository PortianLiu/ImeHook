# 诊断日志

> 本文说明 sp_ImeHook 的两级诊断日志：常驻基线与手动开启的详细日志。
> 注入链路与跨进程通道的背景见 [模块实现机理.md](模块实现机理.md)，
> 目标 App 的逆向结论见 `doubaoime/docs/目标APK逆向分析.md` §6.5。
> 最后更新：2026-11-07

---

## 1. 一句话结论

日志分两级：**常驻部分几乎零成本**（每次按键一次原子自增 + 一次布尔判断），
只记录安装/配置/异常等低频事件与计数；**按键级详细日志默认关闭**，用户在设置页手动开启后才记录键位、候选数、命中走向与耗时，二级开关还可追加展开结果的拼音内容。
所有日志只落在**模块 App 私有目录**，模块不申请 `INTERNET` 权限，不联网上传。

---

## 2. 为什么这样分层

钩子运行在豆包输入法的**输入线程**上，每次按键都会调用
`expandHook`（原生 `imehook.cpp`）。这条路径上的开销会被用户直接感知为「输入变卡」，
因此定下三条纪律：

1. 热路径内**不打印日志**（`__android_log_print` 在 logd 反压时单条可达几十到几百微秒）；
2. 热路径内**不分配内存、不拼字符串、不做 I/O**；
3. 热路径内**不加锁**（详细日志的锁只在手动开启后才可能被触及，且临界区仅几十字节拷贝）。

---

## 3. 两级结构

```
目标进程（豆包输入法）
  expandHook（输入线程）
    ├─ 常驻：atomic 计数 +1、atomic 标志判断        ← 约 1~2ns
    └─ 详细：定长数组写一条事件（互斥锁，无分配）    ← 仅 diag=1 时
         │
         │  轮询线程每 3 秒排空一次（JNI）
         ▼
  HookEntry 后台线程
    ├─ 基线事件（init / 配置下发 / 重启 / 异常）
    └─ nativeDrainDiag() 取走的详细事件
         │  ContentProvider.call("appendLog")
         ▼
模块 App 进程（lpt.imehook）
  └─ LogSink 追加写 files/logs/imehook.log（512KB 滚动，保留 2 份）
         │
         ▼
设置页「诊断日志」卡片：查看 / 导出 / 清空
```

目标进程与模块 uid 不同，写不了对方的私有文件，所以**落盘统一由模块进程代做**：
目标进程只把成批文本通过 Binder 推过去，写盘发生在模块进程的 Binder 线程上，不在输入路径。

## 4. 常驻基线（始终开启，不受开关控制）

触发时机与内容：

| 时机 | 日志行 |
|---|---|
| 目标进程启动、钩子装载 | `[baseline] versionCode=1144 nativeLoaded=true installedNow=true installed=1 unsupported=0 converts=0 custom=0 fallback=0` |
| libshell 延迟装载后补装钩子 | `[baseline] hook installed after libshell loaded installed=1 …` |
| 配置下发（用户点「应用设置」等） | `[baseline] config applied mode=2 slot=6 tableLen=647 diag=true diagc=false` |
| 用户点「重启豆包输入法」 | `[baseline] restart requested by user` |
| 加载 so / 装钩子 / init 抛异常 | `[error] load native failed: …` / `[error] install failed: …` / `[error] init failed: …` |

计数含义（`nativeStats()` 快照）：

| 字段 | 含义 |
|---|---|
| `installed` | 钩子是否已装上（0/1） |
| `unsupported` | 是否命中「未支持的目标版本」分支（0/1） |
| `converts` | `expandHook` 被调用总次数 |
| `custom` | 命中自定义表的次数 |
| `fallback` | 自定义表未覆盖、回退目标槽的次数 |

基线不写文件路径细节、不记录按键，只有版本码、配置与异常 —— 用于判断
「钩子有没有装上 / 配置有没有下发 / 目标版本是否被支持」。

## 5. 详细日志（手动开启）

### 5.1 开关与配置键

`files/config.txt` 头部的两个键（必须位于 `---table---` 之前）：

```
diag=1        # 总开关：记录按键级事件
diagc=1       # 二级开关：额外记录展开结果的拼音内容（仅在 diag=1 时有效）
```

- 默认均为 `0`；
- 设置页关闭总开关时**联动**把 `diagc` 也置 0，并清空尚未排空的缓冲，避免残留按键内容；
- 二级开关在 UI 上随总开关置灰，不能单独开启；
- 配置每秒轮询一次，改动 **1 秒内**在目标进程生效，无需重启。

### 5.2 事件行格式

```
t=360612383537226 d=43437 m=2 s=6 k=er r=1 x=2 v=ou
```

| 字段 | 含义 |
|---|---|
| `t` | 事件时刻，`CLOCK_MONOTONIC` 纳秒（不是墙钟） |
| `d` | 本次 `expandHook` 调用耗时，纳秒（**包含目标自身展开的开销**，不是本模块额外开销） |
| `m` | 生效模式：0 直通 / 1 切换内置槽位 / 2 注入自定义 |
| `s` | 当前目标槽位（1..7） |
| `k` | 参与展开的键，最多 2 个 ASCII 字节；非短串时不记录内容 |
| `r` | 返回候选数（上限 255） |
| `x` | 走向：0 直通 / 1 槽位改写 / 2 自定义命中 / 3 回退目标槽原生 |
| `v` | 展开结果（**仅 `diagc=1` 时出现**），逗号分隔，最多 8 个候选，整体限 96 字节 |

`v` 只保留可打印 ASCII（拼音音节），非可打印字符替换为 `?`。汉字候选**不会**被记录。

### 5.3 缓冲与排空

- 原生侧定长缓冲 `kDiagCap = 512` 条，满则丢弃最旧并累计 `dropped`；
- 轮询线程每 3 秒调用一次 `nativeDrainDiag()`，一次 Binder 推送，写盘在模块进程；
- 若这次有丢弃，尾部会多一行 `dropped=N`；
- 关闭总开关会立即丢弃未排空的缓冲。

### 5.4 文件与容量

```
/data/data/lpt.imehook/files/logs/imehook.log     # 当前日志
/data/data/lpt.imehook/files/logs/imehook.log.1   # 上一份（仅保留一份）
```

- 单文件超过 512KB 时滚动，最旧的一份被删除；
- 设置页「查看」读文件尾部 200KB；「导出」走 SAF，默认文件名 `imehook-log.txt`；
- 「清空」删除两份文件。

## 6. 实测样例

设备上开启 `diag=1 diagc=1` 后键入 `w` `e` `n` `i`：

```text
t=360514901212159 d=9271  m=2 s=6 k=e  r=5 x=3
t=360611724832747 d=41927 m=2 s=6 k=e  r=5 x=3 v=e,ei,en,er,eng
t=360612383537226 d=43437 m=2 s=6 k=er r=1 x=2 v=ou
t=360612383594726 d=1771  m=2 s=6 k=r  r=1 x=2 v=r
```

可读出的信息：

- `k=e x=3 v=e,ei,en,er,eng`：`e` 不在流珀天双拼表内，回退槽 6（小鹤）原生展开出 5 个候选；
- `k=er x=2 v=ou`：自定义表命中，`er → ou`，表内容正确；
- 同一物理按键常出现**成对的两条**记录（时间差 < 1ms），属目标自身两条展开路径，
  不代表重复按键；
- 耗时量级：冷调用 10~40µs（含目标侧 string 构造与查表），随后同一键降到 1µs 级。

## 7. 用它排查「特定音节失效 / 切词错误」

| 现象 | 日志特征 | 结论 |
|---|---|---|
| 某音节完全没有按自定义方案走 | 该键 `x=3` | 表里缺这个键，补表即可，不是 bug |
| 预期 `vh` 被拆成 `v`+`h` 分别展开 | `k=` 序列与预期不符 | 目标侧切词/分段问题，日志是唯一直接证据 |
| 命中了但展开的拼音不对 | `x=2` 且 `v=` 与表内容不符 | 表内容错，修表 |
| 模式看起来没生效 | 全为 `x=0`，基线里 `mode=0` | 配置未下发或保存失败，看 baseline 行 |

注意：`t` 是单调时钟，不能直接对齐 logcat 的墙钟时间；需要对齐时以基线行的
接收时刻为基准换算。

## 8. 隐私与边界

- 详细日志确实包含**按键内容**（关键日志），但只在手动开启后记录；
- 全部日志只存模块私有目录，模块**没有 `INTERNET` 权限**，不存在自动上传；
- 导出由用户主动触发（SAF 选择位置）；
- 「关闭开关」会同时清空未排空的缓冲；「清空」删除全部日志文件；
- 目标进程被停止或模块进程未启动时，推送失败会**静默丢弃**，不影响输入法。

## 9. 常见坑

1. **不要用 `adb` 直接改 `config.txt`**：换行符被改成 CRLF、或插入位置在 `---table---` 之后，
   都会让解析回落默认值（表现为「配置莫名被重置」）。改配置一律走设置页「应用设置」。
2. **改完要确认 mtime 变化**：轮询靠文件修改时间判断，原地覆盖但时间戳不变时不会 reload。
3. **目标进程没启动就没有新日志**：基线只在目标 `init` 时写；先在设置页「查看」确认文件是否存在。
4. **子进程也会写日志**（`:push` / `:upgrade`），同一时刻出现重复的 `config applied` 属正常。
5. **`d=` 不是埋点开销**：它包含目标自身展开的时间，不能用来评估日志成本；
   评估日志成本看「关闭 vs 开启」的体感与 `converts` 增速即可。
6. 详细日志长时间开启且高频输入时，512 条缓冲可能溢出，看到 `dropped=N`
   说明漏采，可缩短排空间隔（当前 3 秒）或临时只开总开关不开二级开关。
