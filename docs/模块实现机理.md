# sp_ImeHook 模块实现机理

> 本文说明「模块怎么把自己注进豆包输入法」——分进程、分层次、按调用时序讲实现，
> 不重复逆向结论。目标函数语义见 `doubaoime/docs/目标APK逆向分析.md` §6.5，
> 定位策略见 `doubaoime/docs/目标APK函数定位与跨版本适配.md`。
> 最后更新：2026-11-06

---

## 1. 一句话总览

LSPosed 把模块代码加载进**豆包输入法自己的进程**里；模块从自己的 APK 解压出一个
native 库，用 Dobby 对 `libshell.so` 的 `sub_59953C` 做 inline hook；
配置不直接读文件，而是通过一个只读 ContentProvider 跨 uid 传进来；
hook 本体是纯内存查表，**热路径零 I/O**。

---

## 2. 进程与职责划分

```
┌───────────────────────────────┐        ┌────────────────────────────────────┐
│  模块进程 lpt.imehook          │        │  目标进程 com.bytedance.…doubaoime  │
│                               │        │                                    │
│  SettingsActivity/Compose UI  │        │  HookEntry (LSPosed 注入)          │
│  SettingsUiState（业务动作）   │        │    ├─ loadNative：解压 + load       │
│  SchemeStore（方案库 prefs）   │        │    ├─ applyConfig：读配置/偏移表    │
│  SchemeParser（ini → 扁平表）  │        │    ├─ nativeTryInstall             │
│  ConfigProvider（只读出口）    │◀──Binder──▶    ├─ loadLibrary0 重试钩子         │
│  LogSink（日志落盘）           │        │    └─ observeConfig（1s 轮询）      │
└───────────────────────────────┘        │                                    │
                                          │  libimehook.so (内存中)             │
                                          │    Dobby → libshell.so 注入点       │
                                          └────────────────────────────────────┘
```

两个进程 uid 不同，这是所有设计取舍的根源：**文件权限、包可见性、日志落盘都跨不过去**，
所以统一走 Binder（ContentProvider）。

## 3. 模块 App 侧

### 3.1 界面

Jetpack Compose + Material 3，单 Activity（`SettingsActivity`）两个 Tab：

| Tab | 内容 |
|---|---|
| 注入 | 模式选择（关闭 / 槽位改写 / 自定义表）、方案选择、目标槽位、试打输入框、状态与诊断卡、重启 |
| 方案管理 | 方案列表、ini 导入、模板导出、结构表编辑（声母/韵母/音节）、零声母设置、重命名/删除 |

`SettingsUiState` 承担全部业务动作（选方案、改模式、试打、发布配置、导出日志），
UI 只读 state，避免「界面显示了但目标进程没生效」的偏差。

### 3.2 方案库

`SchemeStore` 用模块自己进程内的 `SharedPreferences("config")` 存 JSON 数组，每条：

```
name / ini（补全后的原文）/ normalized（归一化结构 JSON）
ziMode / ziKey / ziPriority（零声母处理方式）
```

`active_scheme` 记录当前选中方案。这份数据只在模块进程读写，目标进程拿不到也不需要拿。

### 3.3 码表解析

`SchemeParser` 把 `sp26.ini` 形式（`[sheng]` / `[yun]` / 音节行）解析成引擎同构的三块：

- `exact`：键 → 音节列表
- `a`：首键 → 音节列表（对应引擎 EXACT 表）
- `b`：次键 → 音节列表（对应引擎 PREFIX 表）

导入时自动补全：六个单韵母映射到自身、单字母声母映射到自身、`vn/un`、`ve/ue`、`van/uan`
互为别名、`~` 识别为零声母占位键。零声母有四种处理方式（固定键 / 首字母 / 首字母全拼 / 其它），
导入时猜一种，用户可在管理页改。

最终展开成**扁平表** `双键码 → 音节数组`，逐行 `key=py1,py2` 下发给 native
（`applyZeroInitial` 后调用 `Scheme.scheme.table` 序列化）。native 只需 `unordered_map` 直接查。

### 3.4 配置发布

`ModuleConfig.publish()`：

1. 把 `mode / slot / exit / diag` 与自定义表正文写入模块私有 `filesDir/config.txt`；
2. `notifyChange(CONFIG_URI)` 通知目标进程（实际生效靠目标进程轮询，见 §5.5）。

**为什么不用 `XSharedPreferences`**：LSPosed 会把模块 prefs 重定向到
`/data/misc/apexdata/<uuid>/prefs/lpt.imehook/config.xml`，权限 `0660`、属主是模块 uid，
目标进程（另一个 uid）读不到；`makeWorldReadable()` 也改不了别人的文件，
且每次保存都会被 `0660` 重写。详见 `doubaoime/docs/运行时注入与配置通道.md`。

## 4. 注入入口 `HookEntry`

### 4.1 时序

```
handleLoadPackage(目标包名匹配)
  └─ hook Application.onCreate
       └─ after: init(ctx)
            ├─ loadNative(ctx)                 解压 so → System.load
            ├─ vc = versionCodeOf(target)
            ├─ applyConfig(ctx, first=true)    nativeConfigure + nativeSetTargets + nativeSetDiag
            ├─ nativeTryInstall(vc)            libshell 已加载则当场装上
            ├─ hookLoadLibraryRetry(vc)        libshell 后加载时补装
            └─ observeConfig(ctx)              1s 轮询配置版本
```

**关键顺序**：先 `applyConfig`（内含 `nativeSetTargets`）再 `nativeTryInstall`——
偏移表必须在安装前就位，否则 `tryInstall` 只能查到内置兜底表。

### 4.2 native 库的解压与加载

- 目标 App 的私有目录里没有我们的 so，`System.loadLibrary` 找不到，只能自行解压；
- 从模块 APK 取 `lib/arm64-v8a/libimehook.so`，落到
  `目标 filesDir/imehook/libimehook-<模块APK mtime>.so`；
- 文件名带 APK 修改时间：模块升级后自动换新库，避免加载旧缓存；
- 已存在则跳过解压，直接 `System.load`。

模块 APK 路径由 `ContentProvider /apk` 返回（目标进程受包可见性限制，`PackageManager`
查不到 `lpt.imehook`，因此由 Provider 自报 `sourceDir`）。

### 4.3 libshell 晚加载的重试

`Application.onCreate` 时 `libshell.so` 可能还没被 `dlopen`。
钩 `Runtime.loadLibrary0`（两个重载都钩）的 `after`：库没装上就再试 `nativeTryInstall`，
成功则标记 `sLazyInstalled` 并立刻重新 `applyConfig`（此前 native 配置是空转）。

`tryInstall` 自身有 `g_unsupported` 闸：定位失败过就不再无限重试。

### 4.4 配置变更生效

`observeConfig` 用 `HandlerThread` 每秒查一次 `configVersion`：

- `configVersion` = Provider `query` 返回的「`config.txt` 与 `targets.txt` 的 mtime 取较大者」；
- 值变化才 `applyConfig(ctx, first=false)` 重读正文；
- 值不变时只有一次 Binder 查询（stat 语义），不读文件正文；
- 顺带处理「重启信号」：`exit` 值变化则 `Process.killProcess(Process.myPid())` 自杀
  （不需要 root；用「值变化」而非「有值」判断，避免重启后立刻再自杀的死循环）；
- 详细诊断开启时，每 3 秒排空一次 native 事件缓冲并推给模块进程落盘。

## 5. native 侧 `imehook.cpp`

### 5.1 与目标函数的 ABI 对齐

目标函数返回 `std::vector<std::string>`（24 字节），超过 16 字节 → 走 `x8` sret。
C++ 侧用同布局的自定义结构 + **按值返回**，让编译器自动走 `x8`：

```cpp
struct SpStr { char raw[24]; };              // libc++ std::string 布局
struct SpVec { SpStr *b, *e, *c; };          // {begin, end, cap}
using ExpandFn = SpVec (*)(void* scheme, const SpStr* key);
```

读入参 `spToStr` 区分短串/长串；返回元素只写 **SSO 短串**（`b0 = len<<1`，数据从 `+1`），
拼音最长 6 字节，远小于 22 的 SSO 上限，彻底避开堆生命周期。
vector 缓冲用 `malloc`——Android libc++ 默认分配器最终就是 `malloc/free`，
引擎按移动语义析构时不会崩。

### 5.2 三种模式

| mode | 行为 | 适用 |
|---|---|---|
| 0 关闭 | 直接 `g_orig` | 完全恢复原生 |
| 1 槽位 | 临时把 `*scheme` 首字节改成目标槽 id，调原函数后恢复 | 启用 UI 未暴露的内置方案 |
| 2 自定义 | 先改 id 到目标槽；自定义表命中则自建 vector，未命中回退该槽原生结果 | 注入自己的双拼方案 |

模式 2 的「命中」是 `unordered_map` 查扁平表；返回时把 id 恢复原值，避免污染调用方。
因为 `sub_59953C` 是 7 槽共用的**唯一收口**，一次 hook 即可覆盖所有槽，不需要 7 份。

### 5.3 目标定位

两条路径（详见 `doubaoime/docs/目标APK函数定位与跨版本适配.md`）：

1. **版本表 + 16 字节序言签名**：`versionCode` 命中 + 字节一致 → 零扫描；
2. **特征码扫描**：在 RX 段找「7 槽选表」指令骨架，向前回推函数头，
   要求所有命中收敛到同一函数头，否则判定误命中并放弃。

定位失败置 `g_unsupported`，拒绝 hook（宁可失效也不误钩）。

### 5.4 热路径开销

`expandHook` 每次调用只做：

- 2 次原子读（mode、diag）+ 1 次原子自增（计数）；
- 1 次 `atomic_load`（`shared_ptr<const Table>`，读侧无锁）；
- 1 次 `unordered_map<string, vector<string>>` 查找；
- 命中时 `malloc` 一段 + 若干 SSO 写入。

**无 I/O、无文件、无网络、无全局锁竞争**。目标函数本身在每次按键的每个位置都会被调用
（O(n²) 次/键），这是必须遵守的约束。

### 5.5 诊断

两个层次：

| 层次 | 开关 | 开销 | 用途 |
|---|---|---|---|
| 常驻计数 | 始终开 | 每调用 1 次 relaxed `fetch_add`（~1-2ns） | 总调用数 / 自定义命中 / 回退次数 |
| 详细事件 | 用户手动开 | 每次多 2 次 `clock_gettime` + 加锁写定长数组 | 按键级轨迹、耗时、结果类型 |

详细事件进 512 条定长环形缓冲（超限只增 `dropped` 计数），Java 侧每 3 秒
`nativeDrainDiag()` 取走并清空，经 `ContentProvider.call("appendLog")` 推给模块进程，
由 `LogSink` 落盘（512KB 滚动，保留两份）。**全程目标进程热路径不写文件**。

事件字段：`t`(单调时钟 ns) / `d`(本次耗时 ns) / `m`(模式) / `s`(槽位) / `k`(按键最多 2 字符) /
`r`(候选数) / `x`(结果类型：0 直通 1 槽位 2 自定义命中 3 回退)。

### 5.6 JNI 接口

| 方法 | 作用 |
|---|---|
| `nativeConfigure(mode, slot, table)` | 下发模式与扁平表（重建 `shared_ptr<const Table>` 后原子替换） |
| `nativeTryInstall(versionCode)` | 尝试安装 hook；库未加载返回 false |
| `nativeSetTargets(text)` | 下发偏移表（见 §6） |
| `nativeSetDiag(boolean)` | 详细事件开关；关闭时清空缓冲 |
| `nativeDrainDiag()` | 取走并清空事件缓冲，返回文本 |
| `nativeStats()` | 常驻计数快照 |

## 6. 偏移表持久化（`targets.txt`）

### 6.1 为什么抽出来

硬编码偏移表意味着「新版本必须重新打包模块」。抽到存储后：

- 用户可手动填入未收录版本的偏移（应对渠道包/内测包）；
- 未来可由网络渠道拉取最新表（发版即更新，无需用户升级模块）。

### 6.2 存储格式

模块私有目录 `filesDir/targets.txt`，纯文本，一行一条：

```
# versionCode=offset:signature(16 字节 = 32 个十六进制字符)
100504010=0x59953C:ff4303d1fd7b07a9fc6f08a9fa6709a9
```

空行与 `#` 开头忽略；`offset` 支持 `0x` 前缀或纯十六进制；格式错误的行静默跳过。
选纯文本而非 JSON：用户手填友好，网络拉取后也只需转换成这个格式。

### 6.3 数据流

```
模块进程 targets.txt
   │  ContentProvider /targets（openFile 只读）
   ▼
HookEntry.applyConfig → nativeSetTargets(text)
   │  解析成 vector<TargetInfo>
   ▼
native g_targets（进程启动读入一次，常驻内存）
   │
   ▼  tryInstall 时遍历（加锁仅在替换/读取指针的瞬时）
定位成功
```

### 6.4 兜底

`g_targets` 为空（文件缺失/为空/全部行解析失败）时，自动回落**内置兜底表**
`kBuiltinTargets`（当前仅 1.5.4 一条）。所以 `targets.txt` 不存在不会导致失能。

### 6.5 更新方式

- 文件 mtime 变化会被 `configVersion`（取 `config.txt` 与 `targets.txt` 较大者）捕获；
- 目标进程 1 秒内重读并重新 `nativeSetTargets`；
- 已安装的 hook 不受影响（偏移表只用于**首次定位**，重装不必要）。

## 7. 存储访问清单

| 操作 | 时机 | 频率 |
|---|---|---|
| 解压 `libimehook.so` | 首次加载 / 模块 APK 升级 | 一次 |
| `System.load` | 进程启动 | 一次 |
| 读 `config.txt` 正文 | 启动 + 配置 mtime 变化 | 低频 |
| 读 `targets.txt` 正文 | 启动 + 任一文件 mtime 变化 | 低频 |
| 查配置版本（mtime） | 每 1 秒 | 1 次/秒（只 stat，不读正文） |
| 排空诊断事件 | 诊断开启时每 3 秒 | 1 次/3 秒（关闭时 0） |
| 写日志 | 模块进程侧（`LogSink`） | 仅诊断/基线事件 |
| **按键热路径** | 每次按键每个位置 | **零 I/O** |

结论：注入逻辑**不频繁访问存储**；唯一周期性行为是每秒一次 mtime 查询。

## 8. 已知失败场景与排查

| 现象 | 可能原因 | 排查点 |
|---|---|---|
| 日志无 `[ImeHook] loaded into` | LSPosed 作用域未勾选目标包 / 模块未启用 | LSPosed 模块开关 + 作用域 |
| `nativeLoaded=false` | 模块 APK 路径拿不到 / 解压失败 / ABI 不匹配（仅 arm64） | `load native failed` 日志 |
| `installedNow=false` 且无后续成功 | libshell 未加载且重试未触发 | `hook installed after libshell loaded` 是否出现 |
| `version 100504010 prologue sig mismatch` | 渠道包/热修复改了序言 | 看是否退回 `signature-scan` |
| `signature scan diverged` | 特征码误命中多处 | 需重新提取特征码 |
| `target not found …, unsupported` | 未知版本且特征码不匹配 | 在 `targets.txt` 补一条，或用新版模块 |
| 输入法行为无变化但 hook 已装 | 模式为 0 / 槽位与当前方案不符 / 自定义表为空 | 检查 `configured: mode=… slot=…` 与试打 |
| 输入法崩溃 | 极少数 ROM 下 Dobby 失败或 ABI 误判 | 关闭模块复现；看 `hook FAILED` 日志 |

`DobbyHook` 在深度定制的国产 ROM 上可能因 SELinux / 内核写保护失败，
此时日志为 `hook FAILED`，模块不会尝试其它写入手段。

## 9. 文件地图

| `HookEntry.java` | LSPosed 入口、注入时序、重试、轮询、日志推送 |
